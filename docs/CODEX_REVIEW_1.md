## 1. Bugs and security issues, prioritized

| ID | Priority / location | Evidence, consequence and concrete fix |
|---|---|---|
| B1 | **P1** `app/service.py:340`, `app/service.py:188`, `app/service.py:196`; `app/guardrails.py:171` | **Budget check and reservation are not atomic.** A four-party barrier inside mock `create_order` lets four requests each pass against zero spend: four $49 orders all return `AWAITING_PAYER_APPROVAL`, total **$196 > $150**, no approval. Individual SQLite method locks do not protect the operation, including across processes. Atomically evaluate and insert a provisional reservation in one DB transaction **before** external I/O; persist a recoverable create operation and reconcile uncertain outcomes. |
| B2 | **P1** `app/service.py:367`, `app/service.py:378` | **One approval can authorize multiple orders.** Synchronizing two initial reads of the same PENDING approval produces **two $89 orders, $178 reserved**. Each execution generates a different order/idempotency key. Atomically claim PENDING with a conditional update, enforce a unique approval-to-order relationship, and make approval retries return the existing operation/order. |
| B3 | **P1** `app/main.py:168`, `app/service.py:207`, `app/service.py:268`, `app/service.py:301` | **Cancel/expiry races can erase captured spend.** Pause capture after its open-state check, call unauthenticated `GET /paypal/cancel?token=...`, then resume: PayPal and local order become `COMPLETED`, ledger **$0 instead of $49**. Expiry has the same stale-read pattern. Token protection on POST cancel is bypassed by the GET route, and PayPal IDs are publicly listed. Add a durable CAPTURING state with atomic transitions; serialize cancel/expiry against capture; bind cancellation to an authenticated buyer session or signed return state. |
| B4 | **P1** `app/service.py:211`, `app/service.py:223`; `app/paypal_client.py:206`, `app/agent.py:121` | **Unknown payment outcome is treated as definite failure.** A fake gateway that captures successfully then raises HTTP 500 causes `CAPTURE_FAILED` and releases all spend although provider status is `COMPLETED`. Raw `httpx` transport exceptions instead escape as 500s and leave incomplete operations. Capture status `PENDING` is also incorrectly labeled `COMPLETED` when order status is COMPLETED; missing capture status passes too. Preserve reservations for ambiguous/pending results, query/reconcile provider state, use recoverable capture attempts, and report success only for a confirmed successful capture. Normalize transport errors and preserve partial agent results. |
| B5 | **P1** `app/service.py:359`, `app/service.py:373` | **Approval does not bind the approved quote.** Persist approval for keyboard $89; change catalog price to $499; approving creates a **$499 order while approval row still says $89**. Hard-rule recheck passes because $499 is under $500 and soft caps are waived. Catalog can change across a restart while approvals persist. Bind approval to product, quantity, amount, currency and merchant/version; require fresh approval when any material term changes. |
| B6 | **P1 for shared deployments** `app/main.py:50`, `app/main.py:90`, `app/main.py:97`, `app/main.py:130`; `app/static/app.js:4` | **No requester identity, ownership or rate limit.** Anonymous callers can consume Claude quota, create orders/approval spam, inspect all orders/justifications and trigger capture of buyer-approved orders. Empty token deliberately makes approvals open, including in Sandbox; README's `demo` token is public. Fail closed outside explicit local demo mode; add requester auth/ownership and request/token-cost limits. Avoid persistent approver secrets in localStorage, especially with third-party scripts executing on the page. |
| B7 | **P2 / core scope gap** `app/paypal_client.py:174`, `app/service.py:163` | **Allowed catalog merchant is not tied to the payment recipient.** Sandbox payload contains amount/reference/description, but neither catalog merchant/payee mapping nor item details (`items` argument is ignored). All catalog merchants use the configured app's receiver context. Therefore the demo enforces trusted metadata labels, not actual multi-merchant payment routing or fulfillment. State this explicitly; validate an authoritative merchant-to-payee mapping and itemized quote before claiming real merchant controls. |
| B8 | **P2** `app/offline_agent.py:75`, `app/offline_agent.py:109`, `app/offline_agent.py:141` | **Offline parser purchases despite negation.** `Don't buy any USB-C cables` creates one $12.99 order. Zero quantity is clamped to one; matching has no intent/negation gate. Refuse unsupported negative/conditional language or require confirmation of parsed items before execution. Clearly documenting a restricted grammar is also necessary. |
| B9 | **P2** `app/paypal_client.py:83`, `app/main.py:36` | **Mock checkout breaks across restart.** Orders persist in SQLite, provider mock state does not. Rebuild service on the same DB: old checkout is unknown; capture marks `CAPTURE_FAILED` and releases the reservation. Persist mock provider state or document an isolated reset workflow and invalidate old mock orders deliberately. |

Existing tests cover sequential caps, sequential repeated approval/capture and happy-path reservations. They do not exercise concurrent budgeting, approval claims, capture/cancel interleavings, changed quotes, or ambiguous/pending capture outcomes; the 68 passing tests do not establish these safety properties.

## 2. Guardrail bypass possibilities and boundaries

- **Confirmed:** concurrent orders bypass the daily approval gate (B1); one approval can be multiplied (B2); completed spend can disappear through cancellation races or uncertain outcomes (B3/B4); approved amount can increase silently (B5).
- **Splitting is prevented only by a prompt** (`app/agent.py:30`, `app/service.py:340`). One order of three mice ($73.50) needs approval; three orders of one mouse ($24.50 each) all pass. Reproduced through service calls. A prompted/model-injected sequence can evade the intended purchase-level cap while remaining under the daily cap. Bind purchases to an intent/cart and aggregate related lines/retries; this is a policy-scope limitation, not a failure of the per-order arithmetic.
- **Policy changes do not revoke existing orders:** `capture`/`complete_payment` (`app/service.py:253`, `app/service.py:287`) check lifecycle status, not current hard rules. Reproduced: create cable order, block its merchant, buyer approves, capture still COMPLETED. Decide and document whether existing authorizations are grandfathered; if emergency blocklists should revoke them, recheck at capture with a versioned authorization policy.
- **Prompt injection can redirect permitted spending:** merchant/amount are sourced from the server catalog, which is good, but there is no enforced user-intent budget, task/SKU binding, purchase deduplication or durable request ID. The model can buy unrelated allowed products or repeat a call. Eight model turns do not bound tool calls per turn (`app/agent.py:187`). A timed-out response followed by a user retry can repeat purchases. Add intent-scoped limits and idempotent execution keys; test with scripted malicious tool sequences.
- **Calendar semantics are explicitly reservation-day based** (`README.md`, `app/service.py:196`). A prior-day reservation captured today is absent from today's spend. This matches the documented design, but is not a limit on cash captured per calendar day. Show both measures if that protection is intended.
- Verified positives: tool callers cannot supply arbitrary prices/merchants; direct denied purchases and denied approval requests are rejected; authorized approval rechecks current hard rules. None of the above implies direct access to PayPal secrets by the model.

## 3. README and reproduction problems

1. **“Fully offline” overstates the UI** (`README.md:5`, `app/static/index.html:7`). AG Grid JS/CSS come from jsDelivr; with no CDN, `agGrid` is undefined at `app/static/app.js:46`, aborting initialization before the ask form is wired. Vendor the pinned Community assets and preserve license notices. Dependency bootstrap also needs an index/cache; distinguish installation from offline runtime.
2. **Offline environment must persist across commands** (`README.md:92`, `README.md:117`). Numbered server command omits `AGENT_MODE=offline`, despite the earlier alternative. A prefix on the server command does not affect the CLI; with the sample `.env`, a new CLI command defaults to Claude. Give one complete no-key block with `export AGENT_MODE=offline` and a temporary DB; explain rerun/reset and stale mock orders. Current dependency ranges have no upper bounds/lock (`requirements.txt:1`); pin a tested set for judging.
3. **Claim/evidence mismatch:** `docs/DEVPOST.md:80` asserts a full real buyer-approval/capture loop; `README.md:203` and `docs/VIDEO_SCRIPT.md:19` explicitly leave it pending. Recorded Sandbox smoke output only proves create/status/preapproval refusal/cancel. Remove the completed claim until a real buyer capture is demonstrated. Replace “impossible ... to bypass” (`docs/DEVPOST.md:82`) with the precise protections and known limitations.
4. Public repo/video links remain placeholders (`docs/DEVPOST.md:4`); requirements checklist still marks repository/video/access outstanding. Those are submission blockers, not work performed by this review. Supply the real links and a recorded buyer capture before submission. Offline rules + mock proves mechanics, but cannot independently validate AI + PayPal together. Provide a free, controlled judging path for the actual AI mode or explicit access instructions; do not solve this by committing private credentials.
5. Live Anthropic access and the configured `claude-sonnet-5-5` model were **not verified** here; all agent tests use fakes/offline rules. Confirm the advertised default works through the documented standard endpoint with an ordinary judge account, and record the tested model/date.

## 4. Judging gaps and standout opportunities

Official [rules §§4, 6, 8](https://paypalaihackathon.devpost.com/rules), checked 2026-10-29: functional build access, public licensed repository and public YouTube demo are required; five criteria have equal weight. AG Grid prizes require use of AG Grid tools; Community qualifies. The following are reviewer suggestions, not extra eligibility requirements.

| Target | Current gap | Concrete differentiator |
|---|---|---|
| Technological implementation / PayPal + AI | Real Orders integration is credible, but capture proof and recovery are incomplete; catalog merchant labels overstate payment routing. | Show one real Claude request through Sandbox buyer approval to capture ID, plus one lost-response recovery with unchanged budget. Add verified webhook reconciliation with replay protection and a visible payment timeline. |
| Agentic Commerce / innovation | Shopping over 13 fixed SKUs with hard-coded policies is familiar; most claimed anti-evasion behavior is untested. | Give the agent a bounded onboarding budget, compare two valid bundles, then enforce a cart-level signed quote. | Potential impact | Audience is named, but no evidence of saved effort or prevented loss. | Demonstrate one office manager onboarding a hire; report measured manual actions/time and approval count against the same task. Include one representative user's feedback without inventing outcomes. |
| Presentation | Draft's decisive capture scene is a placeholder; documentation claims more than the evidence. | In under three minutes: audience/problem → mixed request → actual PayPal capture → human approval → hard refusal → adversarial attempt and audit. Keep mock/rules/live badges visible. |
